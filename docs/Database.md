# Misinformation Examination Database

## Overview

Misinformation Examination uses PostgreSQL as its authoritative persistent data store.

This document defines the database schema, database-enforced invariants, and indexes. Product behavior belongs in `Product.md`; application structure and database-access rules belong in `Architecture.md`; endpoint contracts belong in `API.md`.

The schema is intentionally small and uses ordinary PostgreSQL tables, constraints, and indexes. The application accesses it with direct parameterized SQL through the `pg` client. No ORM, query builder, stored-procedure layer, or dedicated migration framework is required.

## Design Principles

1. Store only durable product state.
2. Use primary keys, foreign keys, unique constraints, and check constraints for invariants PostgreSQL can express simply.
3. Keep multi-table product rules in straightforward TypeScript and transactions rather than forcing them into triggers.
4. Prefer simple, normalized tables that directly represent current product concepts. Avoid abstractions intended only for hypothetical future requirements.

## Naming and Data-Type Conventions

- Use `snake_case` for tables, columns, constraints, and indexes.
- Use plural table names.
- Use `integer GENERATED ALWAYS AS IDENTITY` primary keys.
- Use `text` for user-entered and administrator-entered text unless a real database limit is required.
- Use `timestamptz` for timestamps. Configure application/database sessions to use UTC.
- Use `created_at` for creation time and specific timestamps such as `completed_at` where they represent a product event.
- Let PostgreSQL generate identifiers and timestamps.
- Do not use PostgreSQL enums initially; small `text` or `char` fields with check constraints are easier to change through ordinary SQL migrations.
- UUIDs are not needed for the current architecture because identifiers are created by one PostgreSQL database and do not need to be globally unique.

## Tables

### `students`

Stores one row for each Student.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `id` | `integer` identity | No | Primary key. |
| `key` | `text` | No | Key generated by the application and stored in a browser cookie to link the browser's session to a Student. |
| `email` | `text` | Yes | Email address of the Student. |
| `created_at` | `timestamptz` | No | Student creation time. Use DEFAULT NOW().|

Constraints:

- Primary key on `id`.
- UNIQUE (key).
- For the initial release, `email` does not need to be unique, i.e. duplicates may exist.

### `subjects`

Stores the shared Subjects maintained by the Administrator.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `id` | `integer` identity | No | Primary key. |
| `title` | `text` | No | Subject title shown to Students. |

Constraints:

- Primary key on `id`.
- Check that `title` is not empty after trimming.

### `questions`

Stores each Question, its Choices, and the Answer, all of which is maintained by the Administrator.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `id` | `integer` identity | No | Primary key. |
| `subject_id` | `integer` | No | Subject containing the Question. |
| `short_title` | `text` | No | The short title of the Question used in the Session Complete summary table. |
| `question_text` | `text` | No | Prompt shown to the Student. |
| `choice1` | `text` | No | 1st choice. |
| `choice2` | `text` | No | 2nd choice. |
| `choice3` | `text` | Yes | Optional 3rd choice. |
| `choice4` | `text` | Yes | Optional 4th choice. |
| `answer` | `integer` | No | The answer to the question. 1 corresponds with choice1, 2 with choice2, etc. |
| `explanation` | `text` | No | Explanation of the correct Answer. This text may contain Markdown links. |
| `why_it_spreads` | `text` | No | Text for “Why this misconception spreads.” This text may contain Markdown links. |
| `sources` | `text` | No | Sources supporting the Answer. This text may contain Markdown links. |
| `is_active` | `boolean` | No | Whether the Question is eligible for selection into a new Session. Use `DEFAULT true`. |

Constraints:

- Primary key on `id`.
- Foreign key from `subject_id` to `subjects(id)`.
- Checks that `short_title`, `question_text`, `choice1`, `choice2`, `explanation`, `why_it_spreads`, and `sources` are not empty after trimming.
- CHECK(answer >= 1)
- CHECK(answer <= 4)
- answer = 3 requires choice3 IS NOT NULL.
- answer = 4 requires choice4 IS NOT NULL.
- Optional choices must be NULL or nonempty after trimming.
- choice4 requires a choice3

`is_active` is a global Question flag managed directly through SQL. Inactive Questions remain in the database and are excluded only when selecting Questions for a new Session. Existing `session_questions` membership is fixed and remains usable if a Question is later deactivated; retrieval, Guess evaluation, skipping, progress, and completion for those Sessions do not filter on `questions.is_active`.

### `sessions`

Stores active and completed Sessions.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `id` | `integer` identity | No | Primary key. |
| `student_id` | `integer` | No | Student who owns the Session. |
| `subject_id` | `integer` | No | Session Subject. |
| `created_at` | `timestamptz` | No | Session creation time. Use DEFAULT NOW(). |
| `completed_at` | `timestamptz` | Yes | Completion time. NULL while the Session is active. |

Constraints:

- Primary key on `id`.
- Foreign key from `student_id` to `students(id)`.
- Foreign key from `subject_id` to `subjects(id)`.
- UNIQUE (student_id, subject_id)

When `completed_at` is NULL, the Session is active. When `completed_at` is NOT NULL, the Session is completed.
A Session’s Question membership is established when the Session is created, stored in `session_questions`, and does not change after Session creation.

### `session_questions`

Stores the fixed Question membership of a Session and whether each Question has been completed.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `session_id` | `integer` | No | Owning Session. |
| `question_id` | `integer` | No | Question included in the Session. |
| `position` | `integer` | No | Question’s fixed position within the Session, starting at 1. |
| `choice` | `integer` | Yes | The Choice selected. 1 corresponds with choice1, 2 with choice2, etc. 0 corresponds to 'I don't know / Skip'. `NULL` indicates the Student has not yet selected a Choice. |

Constraints:

- Composite primary key on `(session_id, question_id)`.
- Foreign key from `session_id` to `sessions(id)`.
- Foreign key from `question_id` to `questions(id)`.
- UNIQUE (session_id, position)
- CHECK(position >= 1)
- CHECK(choice >= 0)
- CHECK(choice <= 4)

The application must ensure that every Question belongs to the Session's Subject. Session creation inserts the Session and all of its `session_questions` rows in one transaction.
The application should retrieve Session Questions using ORDER BY position.
A Question is incomplete when `choice IS NULL`. `choice` cannot be cleared, i.e. `choice` is never updated to `NULL`.

### `general_feedback`

Stores a Student's general feedback.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `id` | `integer` identity | No | Primary key. |
| `student_id` | `integer` | No | Student who provided the feedback. |
| `feedback` | `text` | No | The general feedback provided by the Student. |
| `created_at` | `timestamptz` | No | Feedback creation time. Use DEFAULT NOW(). |

Constraints:

- Primary key on `id`.
- Foreign key from `student_id` to `students(id)`.
- Check that `feedback` is not empty after trimming.
- Students may submit more than one feedback

### `question_feedback`

Stores a Student's feedback on a specific Question.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `id` | `integer` identity | No | Primary key. |
| `student_id` | `integer` | No | Student who provided the feedback. |
| `question_id` | `integer` | No | Question receiving feedback. |
| `feedback` | `text` | No | The question-specific feedback provided by the Student. |
| `created_at` | `timestamptz` | No | Feedback creation time. Use DEFAULT NOW(). |

Constraints:

- Primary key on `id`.
- Foreign key from `student_id` to `students(id)`.
- Foreign key from `question_id` to `questions(id)`.
- Check that `feedback` is not empty after trimming.
- Students may submit more than one feedback for the same Question.

### `logs`

Stores server-side error, warning, and informational messages for operational troubleshooting.

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `severity` | `text` | No | Log severity. Use `DEFAULT 'error'`; warnings use `warning`; informational actions use `info`. |
| `message` | `text` | No | Non-sensitive log details. |
| `created_at` | `timestamptz` | No | Log creation time. Use `DEFAULT NOW()`. |

Entries in the logs table do not have a primary key.
CHECK (severity IN ('error', 'warning', 'info')).
The application must not store credentials, connection strings, or other secrets in log messages.

## Indexes

Primary keys and unique constraints create their own indexes.
No additional indexes are required initially.
Review actual queries with EXPLAIN if performance becomes a problem.

## Deletion and Update Rules

The product relies on the Administrator's operational promise not to substantively update content: once a Question has been included in any Session, the administrator will not substantively change its prompt, Choices, correct Answer, or Subject. To replace it, deactivate the original Question and create a new Question. Existing Sessions retain the original Question.

All foreign keys use ON DELETE RESTRICT and the default ON UPDATE NO ACTION. No cascading deletion or update is configured.

## Migrations and Seed Data

The initial schema is located in:

```text
database/001_migration_initial.sql
```

The migration creates tables in dependency order:

1. `students`
2. `subjects`
3. `questions`
4. `sessions`
5. `session_questions`
6. `general_feedback`
7. `question_feedback`
8. `logs`

Migration files are ordinary SQL, are committed to source control, and are applied in numeric order. After a migration has been applied to production, do not edit it; create a new numbered migration for corrections.
Every `.sql` filename must begin with its numeric sequence followed by either `migration` or `seed`, using the format `<number>_migration_<description>.sql` or `<number>_seed_<description>.sql`.
Migration and seed files share a single sequence of unique numeric prefixes.
Apply and verify every migration against the development Neon database before applying it to production.
Initial Subjects and Questions seed data may be inserted directly through Neon.
